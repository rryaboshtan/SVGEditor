Why you must sanitize SVG

SVG is not “just an image.” It is XML that can carry active content. Designers export innocent icons; attackers ship the same MIME type with a payload. The moment your app does something like this with user input, you inherit HTML-class XSS risk on your origin: 

// Hostile if `markup` came from an upload or paste
preview.innerHTML = markup;
// or
element.dangerouslySetInnerHTML({ __html: markup });

Teams usually discover this the hard way: a “logo upload,” a paste-to-preview editor, an SVG sprite built from untrusted files, or a share link that embeds raw markup in the URL. Rendering success is not a security signal.

Trusted design-system icons and hostile uploads need different pipelines. Mixing them is how production incidents start.

SVG XSS attack surface (beyond <script>)

Stripping <script> alone is not sanitization. Modern payloads abuse several surfaces at once:

Surface What goes wrong Sanitize response
<script> Direct code execution in page origin Remove the element entirely
on* handlers onload, onclick, onbegin, … Drop every attribute whose local name starts with on
foreignObject HTML island: nested scriptable DOM, forms, iframes Remove (do not “empty and keep”)
SMIL (animate / set) Rewrite href / style to javascript: Remove dangerous animations; never leave retargeting SMIL
URL attributes javascript:, data:text/html, nested SVG data: Allowlist by element kind + scheme
CSS url(javascript:…), @import, legacy bindings Scrub <style> and style=""
External <use> Pull remote SVG content into the document Fragments only (#icon) for untrusted trees
feImage / filters Can reference remote or nested data: content Same URL policy as <image>; block nested SVG data

This matches the spirit of OWASP ASVS 5.2.7: sanitize, disable, or sandbox user-supplied SVG — especially inline script and foreignObject. CSP alone is not enough; SMIL is declarative animation, not “script,” so a strict script-src will not stop an animate that rewrites href.

Payload patterns you should test against

These snippets are hostile examples for security tests — not something to paste into production without a sanitizer. A correct pipeline must neutralize them before DOM insert.

1) Event handler on a shape

<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 24 24">
  <circle cx="12" cy="12" r="10" onload="alert('xss')" />
</svg>

Expectation after sanitize: the onload attribute is gone. The circle may remain.

2) foreignObject HTML island

<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 200 80">
  <foreignObject width="200" height="80">
    <body xmlns="http://www.w3.org/1999/xhtml">
      <script>alert("via foreignObject")</script>
    </body>
  </foreignObject>
</svg>

Expectation: the entire foreignObject subtree is removed. “SVG-only” parsers that ignore HTML namespace children fail here.

3) SMIL rewriting href to javascript:

<svg xmlns="http://www.w3.org/2000/svg" xmlns:xlink="http://www.w3.org/1999/xlink">
  <a xlink:href="#">
    <text y="20">Click me</text>
    <set attributeName="href" to="javascript:alert(1)" begin="0s" />
  </a>
</svg>

Expectation: the dangerous set / animate is removed (or the whole animation dropped). Leaving SMIL that targets href, xlink:href, or style is a classic incomplete allowlist.

4) Nested SVG / HTML in data: URLs

<svg xmlns="http://www.w3.org/2000/svg">
  <image href="data:image/svg+xml,<svg>…payload…</svg>" />
</svg>

Nested SVG inside data: can reintroduce scriptable content. A strict policy allows common raster data URIs (image/png, jpeg, webp, …) and blocks data:image/svg, data:text/html, and data:application/*.

XXE, DOCTYPE, and non-browser XML parsers

Browser DOMParser with "image/svg+xml" is a different beast from a server-side XML stack. On the server, disable DTDs and external entities before you even think about tag allowlists. Billion-laughs / XXE class bugs live in the parser config, not in your script stripper.

  • Reject or strip DOCTYPE and entity declarations on upload
  • Disable external entity resolution in libxml / Xerces / whatever you use
  • Cap input size and node count (zip bombs and pathological trees)
  • Do not “pretty-print” hostile XML through a second parser with looser settings

SVGEditor’s path is browser-first: invalid markup fails closed via parsererror / non-svg root. If you store uploads server-side, apply the XML hardening checklist and the SVG active-content checklist.

Defense-in-depth sanitize pipeline

  1. Classify the source. Design-system file from CI ≠ paste from the internet ≠ share-hash payload.
  2. Parse as SVG XML. Use DOMParser with "image/svg+xml", require a root <svg>, reject parsererror.
  3. Strip active content deepest-first. Forbidden tags, event handlers, hostile SMIL, then scrub CSS and URL attributes.
  4. Insert only cleaned markup under a CSP that does not trust inline script from random strings. Prefer scrubbed DOM append over string innerHTML when you can.

Simplified shape of a browser sanitizer (the real SVGEditor module is stricter and share-aware): 

function sanitizeSvgMarkup(markup, { share = false } = {}) {
  const doc = new DOMParser().parseFromString(markup, "image/svg+xml");
  if (doc.querySelector("parsererror")) throw new Error("Invalid SVG");
  const svg = doc.documentElement;
  if (svg.localName.toLowerCase() !== "svg") throw new Error("Root must be svg");

  // 1) remove script, foreignObject, iframe, …
  // 2) remove on* attributes
  // 3) drop SMIL that targets href/style or carries javascript:
  // 4) scrub <style> / style="" (block @import, url(javascript:), …)
  // 5) URL policy: fragments OK; raster data: OK; javascript: never
  // 6) if share: unwrap <a>, block remote images (anti-phishing chrome)

  return new XMLSerializer().serializeToString(svg);
}

Safe insert paths: img vs inline vs sanitizer

Insert path XSS risk (untrusted) Theming / DOM access When to use
Raw inline / innerHTML High Full Never for uploads
Sanitized inline DOM Acceptable if maintained Full (after policy) Editors, inspectable preview
<img src="…svg"> Lower for script exec Weak (currentColor won’t theme) Static marks, CMS figures
CSS background-image Lower for script exec Decoration only Atmosphere, not controls
Trusted sprite / components Low (if supply chain clean) Strong Design-system UI chrome

Rule of thumb: trusted system icons may be inlined; user SVG gets a hostile pipeline (sanitize ± <img>). For embedding trade-offs beyond security, see SVG → React and SVG → PNG.

Share / embed mode: XSS is not the only threat

Product editors that encode SVG into a URL hash create a second problem: phishing chrome. Even without script execution, a shared SVG can look like a login button that navigates off-site.

SVGEditor’s share/embed path therefore uses a stricter policy on top of the base sanitizer:

  • Unwrap <a> so fake CTAs cannot navigate away
  • Block remote http(s) images and relative remote assets
  • Still allow local fragments (#id) and safe raster data:image/*

Treat share URLs like the file itself. Confidential marks do not belong in public channels — the payload lives in the hash on the recipient’s machine.

SVGEditor uses a purpose-built client sanitizer because preview, download, Data URI, and share encoding all run in the browser with a known threat model. If you build a SaaS upload feature, DOMPurify (or equivalent) plus server-side validation is often the faster path — as long as SMIL and foreignObject are in your test suite.

DOMPurify SVG config (copy-paste starting point)

Use a maintained build of DOMPurify (Cure53). Pin the version, update on a schedule, and treat SVG bypass advisories as pager-worthy. Starting point for untrusted uploads (tune to your product): 

import DOMPurify from "dompurify";

const CLEAN = DOMPurify.sanitize(dirtySvgString, {
  USE_PROFILES: { svg: true, svgFilters: true },
  // Prefer explicit forbids over hoping defaults never change:
  FORBID_TAGS: [
    "script",
    "foreignObject",
    "iframe",
    "object",
    "embed",
    "animate",
    "set",
    "animateTransform",
    "animateMotion",
    "handler",
    "listener",
  ],
  FORBID_ATTR: [], // still rely on DOMPurify's on* stripping; add extras if you allowlist attrs
  ADD_ATTR: [],    // do not casually ADD_ATTR for href without a URL policy
  KEEP_CONTENT: false,
});

// Second pass for share/preview phishing chrome (product-specific):
// - unwrap or remove <a>
// - drop http(s) images / external use
// Or call your purpose-built SVG sanitizer here.

Notes that bite teams in production:

  • Re-enabling foreignObject for “HTML labels” reopens the entire HTML XSS surface — require a trusted-author tier instead.
  • Forbidding the whole SMIL family is the blunt, safe default for uploads. If you must keep decorative motion, allowlist only animations that cannot target href / xlink:href / style and still fuzz from/to/ values for javascript:.
  • On Node, use a maintained isomorphic wrapper and sanitize again before any browser insert — stored XSS loves the “we cleaned it at upload once in 2022” gap.

How to sanitize SVG uploads in React and Next.js

The React footgun is not exotic: 

// ❌ Never with user/upload markup
<div dangerouslySetInnerHTML={{ __html: uploadedSvg }} />

// ✅ Prefer safe preview for untrusted files
<img src={objectUrlOrHttps} alt="" />

// ✅ Or insert only after sanitize + parse
const clean = sanitizeSvg(uploadedSvg);
previewRef.current.replaceChildren(parseSvgElement(clean));
Layer React SPA Next.js
Upload API Sanitize in the API / Worker before store Route Handler / Server Action — same rule
Preview <img> or scrubbed DOM Same; avoid streaming raw SVG into RSC HTML
Icons in UI Trusted SVGR / components only Import from the design-system package
Export to JSX Sanitize first, then convert Same — see SVG → React guide

If you need theming on a user mark, sanitize to a strict subset first, then wrap as a component. Do not “trust the designer’s export” because the upload form has a file picker.

Browser quirks that break naive sanitizers

Quirk Why it matters What to do
Namespaced event attrs Handlers may appear with prefixes / odd casing Strip by localName: anything matching /^on/i
SMIL vs CSP script-src does not stop declarative animation Remove hostile SMIL in the sanitizer
<img src="file.svg"> Scripts generally do not run; theming dies Good for static preview, not for icon systems
Inline SVG in HTML Full active surface in page origin Highest risk path — sanitize or don’t
Mutation after parse Serializing then re-parsing can reshuffle edge cases Sanitize → insert; avoid multi-hop reparse loops
Safari / Firefox gaps Legacy URL / animation behaviors differ at the edges Fail closed; test payloads in ≥2 engines

Regression tests every SVG sanitizer needs

Treat these as CI fixtures (assert: no script, no on*, no javascript: left, foreignObject gone): 

const FIXTURES = [
  ["onload-circle", `<svg><circle onload="alert(1)" /></svg>`],
  ["foreignObject-html", `<svg><foreignObject><script>alert(1)</script></foreignObject></svg>`],
  ["smil-href", `<svg><a href="#"><set attributeName="href" to="javascript:alert(1)" begin="0s"/></a></svg>`],
  ["data-svg", `<svg><image href="data:image/svg+xml,<svg><script>alert(1)</script></svg>" /></svg>`],
  ["css-js-url", `<svg><style>*{fill:url("javascript:alert(1)")}</style></svg>`],
  ["external-use", `<svg><use href="https://evil.example/x.svg#i" /></svg>`],
];

for (const [name, dirty] of FIXTURES) {
  const clean = sanitizeSvg(dirty);
  assert.ok(!/on\\w+\\s*=/i.test(clean), name);
  assert.ok(!/javascript:/i.test(clean), name);
  assert.ok(!/foreignObject/i.test(clean), name);
  assert.ok(!/<script/i.test(clean), name);
}

When you change the allowlist, add a fixture first. Sanitizer regressions are silent until someone pastes a PoC into production.

CSP: second line, not a substitute

A strict Content Security Policy (for example script-src 'self' without 'unsafe-inline') blocks many leftover script gadgets. It does not replace markup sanitization:

  • Some handlers and navigation tricks still create product abuse
  • Shared SVG can socially engineer clicks without executing script
  • Future browser / library gaps should not be your only door lock

SVGEditor pairs page CSP with the sanitizer on purpose: defense-in-depth.

What breaks when you over-sanitize

  • External sprites: <use href="/icons.svg#x"> may be stripped for untrusted trees — correct for uploads, painful for your own icon sheet.
  • Remote illustrations: <image href="https://cdn/…"> blocked in share mode by design.
  • Decorative SMIL / CSS motion: hostile animation targets must go; benign motion may be collateral if your policy is strict.
  • HTML labels in diagrams: foreignObject diagrams will not survive a secure upload path — ask for a different format or trusted-author exception.

Document two tiers: trusted authoring vs untrusted upload. Do not silently “fix” files in a way that looks like a successful brand asset but lost its links.

Production checklist: sanitize SVG uploads

  • Source classified (trusted system vs user vs share payload)?
  • Parse with XML SVG parser; reject non-svg roots?
  • Forbidden tags removed (script, foreignObject, iframe, forms, …)?
  • All on* attributes removed (including namespaced forms)?
  • SMIL that targets href / style or carries javascript: dropped?
  • CSS scrubbed (@import, url(javascript:), legacy bindings)?
  • URL allowlist by element kind; nested SVG data: blocked?
  • External <use> disabled for untrusted content?
  • Share/embed path strips phishing chrome (links, remote images)?
  • CSP enabled as a second layer?
  • Automated tests include foreignObject + SMIL + nested data URI cases?
  • Invalid markup fails closed with a clear error?

How SVGEditor sanitizes in practice

Every paste, upload, download, Data URI export, and share/embed encode path runs through the client sanitizer before the markup is trusted for preview or serialization. Highlights:

  • Removes executable / active tags (script, foreignObject, iframe, form controls, …)
  • Strips event-handler attributes
  • Removes SMIL that can retarget URLs or inject handlers
  • Scrubs CSS text and url() values
  • Enforces a URL policy (blocks javascript:, nested SVG data:, unsafe schemes)
  • Share mode additionally unwraps anchors and blocks remote images so a hash link cannot pose as a phishing page chrome

Nothing is uploaded to a server for “virus scanning theater.” Cleaning happens on-device — same privacy stance as React and PNG export. Open the editor, paste markup, and inspect the preview; active content should already be gone before you hit share or download.

FAQ

Why can SVG cause XSS?

Because SVG can include script, event handlers, HTML via foreignObject, SMIL that rewrites URLs, and CSS payloads. Inline that into your page and it runs with your origin’s privileges.

Is <img> enough to sanitize SVG?

It lowers script-execution risk versus raw inline markup, but it is not a complete policy and it kills theming. Editors and upload features still need an explicit sanitizer before DOM insert or share encoding.

What is foreignObject XSS?

foreignObject embeds HTML (or other namespaces) inside SVG. Attackers nest scriptable HTML there to bypass naïve “SVG tag allowlists.”

Why is SMIL dangerous?

Animations can change href / style to javascript: after your static attribute scan. Strip hostile SMIL; do not only delete <script>.

Should I use DOMPurify?

Yes for many apps — with an SVG-aware config and regression tests. SVGEditor uses a purpose-built sanitizer for preview/share UX; the requirement is the same: maintain it and test bypasses.

Does SVGEditor sanitize in the browser?

Yes — before preview, download, Data URI, and share/embed. Share mode is stricter against phishing chrome. No server round-trip for cleaning.

Can CSP replace a sanitizer?

No. Use both. CSP catches missed script gadgets; the sanitizer defines what markup your product will even accept.

What breaks if we over-sanitize?

External <use>, remote images, rich SMIL, and HTML-in-SVG diagrams. Split trusted vs untrusted pipelines and fail closed with clear errors.

How do I sanitize SVG uploads in React or Next.js?

Never feed raw uploads to dangerouslySetInnerHTML. Sanitize in the API / Server Action, store only cleaned markup, preview via <img> or scrubbed DOM, and keep design-system icons on a trusted import path. See the React / Next.js section above.

What is a good DOMPurify config for SVG?

Enable the SVG profile, forbid script / foreignObject / hostile SMIL, keep the library updated, and add fixtures for nested data: SVG. Copy the starting config and tighten for share mode.

Does OWASP require sanitizing user SVG?

Yes — ASVS 5.2.7 requires sanitizing, disabling, or sandboxing user-supplied SVG scriptable content (inline scripts and foreignObject called out explicitly).
