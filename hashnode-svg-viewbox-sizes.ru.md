Выгружаешь из Figma иконку 24×24. В браузере она оказывается маркой, билбордом или чётким path’ом, запертым внутри мыльного PNG. Файл почти никогда не «сломан». Он рассказывает **три истории про размер сразу** — а тулчейн выбрал не того рассказчика.

Большинство советов схлопывают это в фразу *«не трогай viewBox»*. Нужно. Но недостаточно. Если ведёшь дизайн-систему, оборачиваешь SVG в React JSX или экспортируешь PNG под email, важно понимать: какой размер — **контракт**, а какие два — просто дефолты.

В этом разборе: чем `viewBox` отличается от `width`/`height` и CSS, почему React «ломает» размер иконки, как посчитать retina PNG (1×/2×/3×) и что проверить за 60 секунд.

## SVG viewBox vs width/height vs CSS — три размера

Типичный экспорт из дизайн-тула выглядит безобидно:

```xml
<svg
  xmlns="http://www.w3.org/2000/svg"
  width="24"
  height="24"
  viewBox="0 0 24 24"
>
  <path d="…" />
</svg>
```

Три независимых сигнала:

| Сигнал | Задача | Кто слушает |
| --- | --- | --- |
| **`viewBox`** | Внутренняя система координат: «рисунок живёт в пространстве 24×24». | Рендереры, `preserveAspectRatio`, любой вменяемый пайплайн иконок |
| **Атрибуты `width` / `height`** | Дефолтный **презентационный** размер, пока никто другой не победил | Браузер (если CSS молчит), часть PNG-растеризаторов, наивный копипаст |
| **CSS / props** (`className`, `width={32}`) | Каким должен быть **этот экземпляр** в приложении | React, вёрстка, дизайн-токены |

Когда они расходятся, получаешь классику:

- В `<img src="icon.svg">` всё ок, в inline JSX — нет
- `<Icon width={16} />` «ничего не делает» (побеждает CSS или порядок атрибутов)
- Retina PNG мыльный: растрировали **атрибутный** размер, а не CSS-размер, которым реально показывают
- `viewBox="0 0 24 24"`, а path’ы рисовали в `0…100` → пустые поля или обрезанный глиф

**Правило:** `viewBox` — контракт. Атрибуты — дефолт. Props/CSS — экземпляр.

## Как работает размер SVG: пространство, маппинг, пиксели

Думай про SVG как про canvas с синтаксисом XML:

1. **Пространство автора** — числа в `d`, `cx`, `x`, … живут в единицах `viewBox`.
2. **Маппинг** — рендерер натягивает этот бокс на viewport (CSS-коробку или пиксельную сетку).
3. **Пиксели** — появляются только когда кто-то просит битмап: PNG, `<canvas>`, скриншот, flatten в PDF.

Если маппинг кривой, крутить `stroke-width` бесполезно — сначала почини `viewBox` и то, куда его проецируют.

### Пример: padding во фрейме 24×24

Дизайн-тулы обожают схему «фрейм 24, глиф ~16, по центру»:

```xml
<svg width="24" height="24" viewBox="0 0 24 24">
  <!-- глиф примерно занимает 4…20 по обеим осям -->
  <path d="M8 6h8v12H8z" />
</svg>
```

| Что делаешь | Результат |
| --- | --- |
| Inline в кнопке 24px | Нормально |
| Растр 24×24, потом PNG показывают как 16 CSS px | Мыльные края |
| Убрать `width`/`height`, оставить `viewBox`, размер через CSS/props | Чётко при любом px |

Иконочные системы хотят третью строку.

### Почему viewBox «не работает»: враньё в координатах

```xml
<!-- path’ы в пространстве 0…100, viewBox врёт -->
<svg width="24" height="24" viewBox="0 0 24 24">
  <circle cx="50" cy="50" r="40" />
</svg>
```

Центр круга вне объявленного бокса. Ты «чинишь» размер в CSS — и всё равно видишь обрезанный диск. Сломан **контракт `viewBox`**, не стили кнопки.

## Почему React ломает размер SVG-иконки

Браузеры прощают грязный HTML. React вытаскивает спор в порядок props:

```jsx
// В файле дефолт 24. На call site — 16. Кто победит?
export function Icon(props) {
  return (
    <svg
      viewBox="0 0 24 24"
      width={24}
      height={24}
      fill="none"
      {...props}
    >
      <path d="…" stroke="currentColor" strokeWidth={1.5} />
    </svg>
  );
}

<Icon width={16} height={16} className="text-slate-700" />
```

Если `{...props}` в конце — побеждает `16`. Перенеси spread выше — call site тихо проигрывает. Команда может неделю спорить про «сломанные иконки», пока кто-то не посмотрит порядок атрибутов.

Более чистый дефолт для UI-хрома:

```jsx
export function Icon({ size = 24, ...props }) {
  return (
    <svg
      viewBox="0 0 24 24"
      width={size}
      height={size}
      fill="none"
      aria-hidden="true"
      {...props}
    >
      <path d="…" stroke="currentColor" strokeWidth={1.5} />
    </svg>
  );
}
```

`viewBox` не трогай. Один API размера. Не заколачивай второй размер в CSS и третий — в PNG-пайплайне.

В React Native та же идея: числовые props (`width={24}` на `<Svg>`). Контракт тот же: `viewBox` в ассете, размер на call site. Если нужен быстрый JSX / RN из разметки — удобно прогнать файл через [SVG → React конвертер](https://getsvgeditor.com/svg-to-react) и сразу проверить props на превью.

## Почему PNG из SVG мыльный на retina

PNG плевать на дизайн-токены. Ему важно только **сколько пикселей ты попросил у растеризатора**.

Типичный провал на хендоффе:

1. В SVG атрибуты `width`/`height` = 24×24  
2. Экспортируешь PNG 24×24  
3. Показываешь на 48 CSS px на экране 2× **без** 2×-ассета  
4. Тикет: «SVG плохо выглядит»

С SVG всё было ок. Запечён неверный pixel budget. Подробный playbook по прозрачности и 2× — в [гайде SVG to PNG](https://getsvgeditor.com/blog/svg-to-png).

### Таблица: CSS-размер → DPR → PNG

| CSS-слот | DPR | Какой PNG экспортировать |
| --- | --- | --- |
| 24×24 | 1× | 24×24 |
| 24×24 | 2× | 48×48 |
| 16×16 | 2× | 32×32 |
| 24×24 | 3× | 72×72 |

Никогда не апскейль 16px PNG в CSS и не называй это retina.

### Чеклист перед экспортом SVG в PNG

1. `viewBox` совпадает с реальными границами path (без сюрприз-кропа)  
2. Сначала реши **CSS display size** (email, CMS — что угодно)  
3. Умножь на нужный DPR — потом экспорт  
4. Прозрачность предпочтительнее; flatten на белый — только если хост требует  
5. Если хост умеет SVG (современный web UI) — PNG часто не нужен

Когда экспорт «мягкий», а path’ы в порядке, перестань гадать: вставь разметку, подвигай `width`/`height` напротив превью, скачай 1×/2× с вкладки PNG. Этот цикл удобно гонять в [онлайн SVG → PNG](https://getsvgeditor.com/svg-to-png) на [getsvgeditor.com](https://getsvgeditor.com): один файл, три размера, маппинг видно сразу.

## Inline SVG vs img vs React-компонент

| Подход | Контроль размера | Темизация | Когда выигрывает |
| --- | --- | --- | --- |
| `<img src="*.svg">` | CSS на коробке картинки | Слабо (`currentColor` файл не темизирует) | Статичные лого, CMS |
| Inline SVG | CSS + атрибуты | Сильно | Разовая иллюстрация на странице |
| React / RN компонент | props + токены | Сильно | Иконки дизайн-системы, повторяемый хром |

Баги размера есть во всех трёх. Компоненты просто делают контракт явным: **`viewBox` в файле, размер на call site**.

## Аудит SVG-иконки за 60 секунд

1. Есть честный root `viewBox`? Не выдумывай `0 0 24 24`, если арт — `0 0 20 20`.  
2. Атрибуты `width`/`height` дублируют размер, который уже задаёт CSS? Убери или выровняй под дефолтный токен.  
3. В JSX call site может переопределить `size` и `aria-*` через порядок `{...props}`?  
4. На UI-хроме жёсткий `#000`? Лучше `currentColor` (не тот цвет + не тот размер = «иконка сломана»).  
5. Нужен PNG? CSS size → × DPR → растр. Крошечный битмап не апскейлить.

## Как зафиксировать размер SVG в команде

Запиши один раз — и хватит открывать спор на каждом PR:

- **Авторство:** один квадратный `viewBox` (24 *или* 20 — выберите одно).  
- **Web:** компоненты с `size` + `currentColor`; без правок path’ов на каждый инстанс.  
- **Email / старые хосты:** PNG в 2×, в шаблоне размер = 1× CSS-слот.  
- **Пайплайн:** SVGR (или аналог), когда `.svg` идут потоком; paste-to-JSX — когда нужен один компонент и живое превью сейчас.

Три размера никуда не денутся. В проде спокойно только когда **одному** из них разрешено спорить.

## FAQ: частые вопросы про размер SVG

### Чем viewBox отличается от width и height в SVG?

`viewBox` задаёт **систему координат** рисунка. `width`/`height` — лишь дефолтный **презентационный** размер, пока CSS или props не перебьют его. Для иконок контракт — `viewBox`; размер экземпляра задавай снаружи.

### Почему SVG из Figma в браузере другого размера?

Часто одновременно живут три сигнала: `viewBox`, атрибуты `width`/`height` и CSS. Дизайн-тул экспортирует все сразу; приложение слушает не то, что ожидал дизайнер. Плюс глиф может занимать не весь фрейм 24×24.

### Почему PNG из SVG мыльный на Retina?

Ты растрировал 1× (например 24×24), а показываешь в слоте 24 CSS px на экране 2× — браузеру не хватает пикселей. Экспортируй 48×48 для слота 24×24 при DPR 2.

### viewBox есть, а иконка обрезана. Почему?

Координаты path/`cx`/`cy` не совпадают с объявленным `viewBox` (классика: арт в `0…100`, бокс `0 0 24 24`). Чини `viewBox` по реальным границам, не «размер кнопки» в CSS.

### Как правильно задать размер SVG в React?

Держи стабильный `viewBox`, один API вроде `size`, и клади `{...props}` так, чтобы call site мог переопределить размер и `aria-*`. Не дублируй третий размер жёстко в CSS и четвёртый в PNG-пайплайне.

### Когда лучше оставить SVG, а когда нужен PNG?

Для современного web UI и темизации — SVG/компонент. PNG — для email, старых CMS и мест, где хост не принимает SVG. Тогда считай CSS-слот × DPR и экспортируй прозрачный битмап осознанно.
